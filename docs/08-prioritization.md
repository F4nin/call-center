# Приоритизация требований

## 1. Цель

Приоритизация помогает определить, какие требования важнее реализовать в первую очередь, а какие можно перенести на последующие этапы.

В учебном кейсе используется модель Value / Cost / Risk. Все оценки являются предварительными экспертными оценками и не подтверждены реальным заказчиком.

## 2. Формула расчёта

Приоритет = Value / (Cost+ Risk)

Где:

- **Value** — относительная ценность требования;
- **Cost** — относительная стоимость реализации;
- **Risk** — относительный риск реализации.

Чем выше результат, тем привлекательнее требование с учётом его ценности, стоимости и риска. Расчёт используется для сравнения требований, но сам по себе не заменяет оценку обязательности и зависимостей между ними.

## 3. Приоритизация функциональных требований

| Требование | Value | Cost | Risk | Расчёт | Приоритет |
|---|---:|---:|---:|---|---:|
| Приём события телефонии, поиск клиента и создание обращения — FR-001, FR-002, FR-003 | 95% | 20% | 10% | 95 / (20 + 10) | 3,17 |
| Назначение ответственного по BR-002 — FR-004 | 80% | 15% | 10% | 80 / (15 + 10) | 3,20 |
| Отправка уведомления клиенту — FR-007 | 75% | 15% | 5% | 75 / (15 + 5) | 3,75 |
| Обработка повторного обращения в течение 24 часов — FR-006 | 70% | 30% | 15% | 70 / (30 + 15) | 1,56 |
| Выбор дежурного оператора — FR-010 | 50% | 15% | 10% | 50 / (15 + 10) | 2,00 |

### Интерпретация результатов

Наивысший расчётный приоритет имеет отправка уведомления клиенту — FR-007. Следом идут назначение ответственного и основной поток обработки звонка.

FR-006 имеет более низкий расчётный показатель, поскольку в исходной оценке для него указаны более высокие стоимость и риск. Однако низкий балл не означает, что требование можно автоматически исключить из первого релиза: оно связано с бизнес-правилом BR-003 и основным сценарием UC-01.

Для FR-010 расчётный приоритет равен ровно 2,00. Следовательно, требование не проходит порог «строго выше 2,00», если использовать исходный критерий буквально.


## 4. Приоритизация нефункциональных требований

В исходной оценке численные значения Value / Cost / Risk приведены только для двух нефункциональных требований.

| Требование | Value | Cost | Risk | Расчёт | Приоритет |
|---|---:|---:|---:|---|---:|
| NFR-01: создание обращения не более чем за 2 секунды | 90% | 10% | 10% | 90 / (10 + 10) | 4,50 |
| NFR-06: TLS 1.2 или выше для интеграций | 100% | 5% | 5% | 100 / (5 + 5) | 10,00 |

Эти значения сохранены из исходной оценки. Численные приоритеты для остальных NFR не рассчитывались, поскольку для них нет исходных значений Value, Cost и Risk.

При этом для всех NFR сохраняются ранее указанные приоритеты MoSCoW:

- **Must:** NFR-01, NFR-03, NFR-04, NFR-05, NFR-06.
- **Should:** NFR-02, NFR-07.
- **Could:** NFR-08, NFR-09.

Для обязательных требований Must высокий или низкий результат формулы не отменяет необходимости их выполнения.

## 5. Рекомендуемое распределение по релизам

Поскольку кейс учебный, ниже приведён рекомендуемый план, а не согласованный с заказчиком график реализации.

### Релиз 1 — основной рабочий сценарий

В первый релиз рекомендуется включить:

- **FR-001, FR-002, FR-003:** получение события, поиск клиента и создание обращения;
- **FR-004:** назначение ответственного по правилам;
- **FR-005 и FR-007:** постановка уведомления в очередь при недоступности сервиса и инициирование отправки;
- **FR-006:** проверка существующего открытого обращения и его повторное использование;
- **FR-009:** обработка ситуации, когда клиент не найден;
- **FR-010:** обработка ситуации, когда нет доступного оператора;
- **FR-011 и FR-012:** отображение карточки оператору и обработка некорректного номера.

В релиз также входят обязательные NFR со статусом Must: NFR-01, NFR-03, NFR-04, NFR-05 и NFR-06.

**Почему FR-006 остаётся в первом релизе:** правило BR-003 уже входит в согласованную логику основного сценария. Перенос его реализации потребовал бы отдельно пересмотреть use case и бизнес-правило. Для текущего учебного кейса проще сохранить согласованность требований и оставить FR-006 в первом релизе, даже несмотря на его более низкий численный приоритет.

### Следующие релизы и бэклог

После реализации основного сценария можно рассмотреть:

- **NFR-02:** проверку работы под нагрузкой в 200 одновременных звонков;
- **NFR-07:** журналирование изменений прав операторов;
- **NFR-08 и NFR-09:** дополнительную проверку удобства использования и оценку времени обучения.

Такое распределение предварительное. Перед реальной разработкой необходимо проверить обязательность каждого требования и зависимости между ними.

## 6. Принципы принятия решений

При определении состава релиза применяются следующие правила:

1. Численный приоритет Value / Cost / Risk используется для сравнения требований, но не является единственным основанием для исключения требования из релиза.
2. Требования Must сохраняют обязательность независимо от численного результата.
3. Требования, от которых зависит основной сценарий или выполнение бизнес-правила, нельзя переносить без проверки влияния на остальные артефакты.
4. Исключённые из объёма проекта функции не включаются в план релизов текущего кейса.
5. Изменения состава релиза должны отражаться в реестре требований, use case и матрице трассируемости.

## 7. Открытые вопросы

- Нужно ли пересчитать Value / Cost / Risk после уточнения состава первого релиза?
- Какие именно показатели будут использоваться для оценки стоимости и риска в реальном проекте?
- Какие критерии приёмки обязательны для каждого требования первого релиза?

До появления дополнительной информации оценки считаются предварительными.

## 8. Итог

Модель Value / Cost / Risk помогает сравнить требования с учётом ценности, стоимости и риска. Однако план релизов должен также учитывать обязательность требований, основной пользовательский сценарий и бизнес-правила.

В этом кейсе FR-006 сохраняется в первом релизе ради согласованности с UC-01 и BR-003. Отчётность и исходящие звонки остаются за пределами текущего объёма проекта.
