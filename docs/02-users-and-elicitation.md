# 02. Пользователи и выявление требований

**Проект:** Автоматизация обработки входящих обращений Call-центра  
**Тип проекта:** Самостоятельный учебный кейс по системному анализу  
**Статус документа:** Учебная версия

## 1. Цель этапа

Цель этапа — определить основного пользователя системы, заинтересованные стороны, внешние системы и предполагаемые методы выявления требований.

Результатом является модель участников проекта и план получения информации, необходимой для детализации требований к системе автоматизации обработки входящих звонков.

**Ограничение:** реальные интервью, семинары и другие мероприятия со стейкхолдерами не проводились. Участники и методы выявления требований определены автором самостоятельно в рамках учебного сценария.

## 2. Пользователи и заинтересованные стороны

В рамках кейса выделены основной пользователь системы, заинтересованные стороны и получатель уведомлений.

| Участник | Роль в кейсе | Задачи и интересы | Взаимодействие с системой |
|---|---|---|---|
| Оператор Call-центра | Основной пользователь | Получение информации о клиенте и обращении, работа с обращением, обработка нестандартных ситуаций | Просматривает карточку клиента и обращение |
| Руководитель Call-центра | Заинтересованная сторона | Определение бизнес-целей, правил назначения ответственных и требований к процессу обслуживания | Влияет на требования к бизнес-процессу; отдельный пользовательский функционал для руководителя в текущем кейсе не рассматривается |
| Клиент | Получатель уведомлений | Получение подтверждения о регистрации обращения | Получает уведомление по доступному каналу связи; доступа к системе не имеет |
| Администратор CRM | Техническая заинтересованная сторона | Обеспечение доступности CRM, настройка интеграции и корректности справочных данных | Взаимодействует с внешней CRM, а не с разрабатываемой системой напрямую |

Роли и интересы участников сформированы как допущения учебного сценария и требуют проверки в реальном проекте.

## 3. Внешние системы

Система автоматизации взаимодействует с тремя внешними системами.

| Система | Назначение | Какая информация необходима |
|---|---|---|
| Телефония | Передача информации о входящем звонке | Формат события, номер телефона, идентификатор звонка, правила повторной отправки события |
| CRM | Поиск клиента и создание обращения | Методы API, структура данных клиента, обязательные поля обращения, возможные ошибки |
| Сервис уведомлений | Отправка уведомлений клиенту | Доступные каналы связи, формат запросов, статусы отправки, обработка ошибок |

В рамках учебного кейса существование необходимых возможностей предполагается. Фактическая проверка документации и контрактов внешних API не выполнялась.

## 4. План выявления требований

Для каждого участника и внешней системы определены предполагаемые методы получения информации.

| Участник или источник | Предполагаемый метод | Что необходимо выяснить |
|---|---|---|
| Операторы Call-центра | Интервью, разбор пользовательских сценариев | Текущий порядок обработки звонка, необходимые данные, типичные исключения |
| Руководитель Call-центра | Интервью | Бизнес-цели, правила назначения ответственных, показатели качества обслуживания |
| Информация о взаимодействии с клиентами | Анализ существующих документов и шаблонов уведомлений | Содержание уведомления, каналы связи, требования к подтверждению регистрации обращения |
| Администратор CRM | Анализ API-документации и техническое интервью | Возможности поиска клиентов и создания обращений, ограничения интеграции |
| Телефония | Анализ API-документации | Формат события, состав данных, ошибки и таймауты |
| Сервис уведомлений | Анализ API-документации | Форматы запросов, доступные каналы, статусы доставки и правила повторной отправки |


## 5. Требования, выявленные при анализе сценария

В ходе самостоятельной проработки сценария выделены следующие группы требований:

- автоматический поиск клиента по номеру телефона;
- создание обращения в CRM;
- автоматическое назначение ответственного согласно бизнес-правилам;
- отправка уведомления клиенту;
- отображение карточки клиента и обращения оператору;
- обработка ситуации, когда клиент не найден;
- обработка ошибок взаимодействия с внешними системами;
- обработка повторных звонков при наличии открытого обращения;
- ручное назначение обращения, если подходящий дежурный оператор отсутствует.


## 6. Учёт неявных требований

При анализе сценария важно учитывать не только явно описанные функции, но и условия, необходимые для достижения бизнес-целей.

**Автоматическое назначение ответственного.** Это поведение должно быть сформулировано как явное требование и связано с соответствующим бизнес-правилом.

**Обработка ситуации, когда нет подходящего оператора.** В текущем варианте системы обращение передаётся дежурному оператору. Если дежурный оператор отсутствует, обращение получает статус «Требует ручного назначения».

Автоматическая очередь с последующим назначением освободившегося оператора в текущий сценарий не входит.

Эти решения являются принятыми допущениями учебного кейса и в реальном проекте должны быть подтверждены ответственными за бизнес-процесс.

## 7. Результаты этапа

По итогам этапа сформированы:

- перечень участников и заинтересованных сторон;
- определение основного пользователя системы;
- перечень внешних систем;
- план предполагаемых методов выявления требований;
- список основных функциональных областей;
- перечень неявных требований и принятых допущений.

Полученные результаты используются на следующих этапах для разработки пользовательских историй, use cases, функциональных требований и бизнес-правил.
