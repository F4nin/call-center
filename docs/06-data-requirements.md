# 06. Требования к данным

**Проект:** Автоматизация обработки входящих обращений Call-центра  
**Тип проекта:** Самостоятельный учебный кейс по системному анализу  
**Статус документа:** Учебная версия

## 1. Цель документа

Документ описывает логическую модель данных системы автоматизации обработки входящих звонков.

В рамках этапа определяются:
- основные сущности и их атрибуты;
- связи между сущностями;
- типы данных и ограничения;
- допустимые значения атрибутов;
- правила целостности данных;
- связь модели данных с бизнес-правилами и функциональными требованиями.

## 2. ERD

Диаграмма сущностей и связей представлена в файле [`diagrams/erd.puml`](../diagrams/erd.puml).

Модель включает пять сущностей:

| Сущность | Назначение |
|---|---|
| `Client` | Клиентские данные |
| `ClientContact` | Контакты клиента и информация об их использовании |
| `Ticket` | Обращение |
| `Operator` | Данные оператора Call-центра |
| `Notification` | Информация об отправке уведомления клиенту |

В модели также используются перечисления для статусов обращений, статусов операторов, ролей операторов, каналов связи и статусов уведомлений.

## 3. Связи между сущностями

| Связь | Описание |
|---|---|
| `Client` — `ClientContact` | Один клиент может иметь несколько контактов. Каждый контакт относится к одному клиенту |
| `Client` — `Ticket` | Один клиент может иметь несколько обращений. Обращение может быть создано без привязки к клиенту |
| `Operator` — `Ticket` | Один оператор может быть ответственным за несколько обращений. У обращения может отсутствовать назначенный ответственный |
| `Ticket` — `Notification` | Одно обращение может иметь несколько связанных уведомлений |
| `ClientContact` — `Notification` | Один контакт может использоваться для нескольких уведомлений. Каждое уведомление связано с одним контактом |

Связи между сущностями описывают логические отношения предметной области. При реализации интеграции с CRM необходимо отдельно определить, какие из этих связей являются физическими внешними ключами, а какие поддерживаются через идентификаторы и API.

## 4. Описание сущностей и атрибутов

### 4.1. Client — клиент

| Атрибут | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | UUID | PK, NOT NULL | Идентификатор клиента |
| `first_name` | VARCHAR(50) | NOT NULL | Имя клиента |
| `last_name` | VARCHAR(50) | NOT NULL | Фамилия клиента |
| `phone_number` | VARCHAR(20) | NOT NULL, UQ | Номер телефона клиента |
| `created_at` | TIMESTAMP | NOT NULL | Дата и время создания записи |
| `updated_at` | TIMESTAMP | NULL | Дата и время последнего изменения |

Источник данных — CRM. В рамках текущего сценария система использует клиентские данные для поиска и обработки входящего звонка.

### 4.2. ClientContact — контакт клиента

| Атрибут | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | UUID | PK, NOT NULL | Идентификатор контакта |
| `client_id` | UUID | FK, NOT NULL | Идентификатор клиента |
| `channel` | Channel | NOT NULL | Канал связи |
| `address` | VARCHAR(255) | NOT NULL | Адрес или идентификатор для отправки |
| `used_at` | TIMESTAMP | NULL | Время последнего использования контакта |
| `created_at` | TIMESTAMP | NOT NULL | Дата и время создания записи |
| `updated_at` | TIMESTAMP | NULL | Дата и время последнего изменения |

Сущность используется для выбора контакта согласно BR-004. При наличии нескольких контактов система выбирает последний использованный контакт.

### 4.3. Ticket — обращение

| Атрибут | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | UUID | PK, NOT NULL | Идентификатор обращения |
| `client_id` | UUID | FK, NULL | Идентификатор клиента |
| `assigned_to` | UUID | FK, NULL | Идентификатор ответственного оператора |
| `status` | TicketStatus | NOT NULL | Статус обращения |
| `source_call_id` | VARCHAR(100) | NOT NULL, UQ | Идентификатор звонка в источнике |
| `created_at` | TIMESTAMP | NOT NULL | Дата и время создания обращения |
| `updated_at` | TIMESTAMP | NULL | Дата и время последнего изменения |

Обращение создаётся в CRM. Поле `client_id` может быть пустым, если клиент не найден. Поле `assigned_to` может быть пустым, если требуется ручное назначение.

Уникальность `source_call_id` предотвращает создание нескольких записей обращения с одним идентификатором исходного звонка. Это ограничение не заменяет BR-003, поскольку бизнес-правило также предусматривает обработку разных звонков с одного номера в течение 24 часов.

### 4.4. Operator — оператор

| Атрибут | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | UUID | PK, NOT NULL | Идентификатор оператора |
| `first_name` | VARCHAR(50) | NOT NULL | Имя оператора |
| `last_name` | VARCHAR(50) | NOT NULL | Фамилия оператора |
| `role` | OperatorRole | NOT NULL | Роль оператора |
| `status` | OperatorStatus | NOT NULL | Текущий статус оператора |
| `is_duty` | BOOLEAN | NOT NULL, DEFAULT FALSE | Признак дежурного оператора |
| `created_at` | TIMESTAMP | NOT NULL | Дата и время создания записи |
| `updated_at` | TIMESTAMP | NULL | Дата и время последнего изменения |

Сущность используется для определения ответственного согласно BR-002 и BR-005.

Источник справочника операторов и способ получения актуального статуса смены в текущем кейсе не определены.

### 4.5. Notification — уведомление

| Атрибут | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | UUID | PK, NOT NULL | Идентификатор уведомления |
| `ticket_id` | UUID | FK, NOT NULL | Идентификатор обращения |
| `contact_id` | UUID | FK, NOT NULL | Идентификатор выбранного контакта |
| `channel` | Channel | NOT NULL | Канал отправки |
| `status` | NotificationStatus | NOT NULL | Статус уведомления |
| `created_at` | TIMESTAMP | NOT NULL | Дата и время создания уведомления |
| `sent_at` | TIMESTAMP | NULL | Дата и время отправки |

Сущность используется для учёта отправки уведомлений и обработки ситуации, когда внешний сервис уведомлений недоступен.

В текущей модели предусмотрены статусы уведомления, но способ хранения очереди и выполнения повторных попыток отдельно не специфицирован.

## 5. Перечисления

### 5.1. TicketStatus

| Значение | Назначение |
|---|---|
| `CREATED` | Обращение создано |
| `ASSIGNED` | Ответственный назначен |
| `IN_PROGRESS` | Обращение находится в работе |
| `RESOLVED` | Обращение решено |
| `REJECTED` | Обращение отклонено |
| `REQUIRES_CLIENT` | Требуется уточнение клиента |
| `REQUIRES_MANUAL` | Требуется ручная обработка или назначение |

В Use Case используются бизнес-обозначения «Открыто», «Требует уточнения клиента» и «Требует ручного назначения». Технические значения должны быть согласованы с этими обозначениями в едином словаре статусов.

### 5.2. Channel

Допустимые значения:
- `SMS`;
- `EMAIL`;
- `PUSH`.

### 5.3. OperatorStatus

| Значение | Назначение |
|---|---|
| `ACTIVE` | Оператор активен |
| `ON_BREAK` | Оператор на перерыве |
| `OFFLINE` | Оператор недоступен |

### 5.4. OperatorRole

Допустимые значения:
- `OPERATOR`;
- `SUPERVISOR`;
- `ADMIN`.

Наличие значений `SUPERVISOR` и `ADMIN` в модели не означает, что отдельные функции руководителя и администратора входят в текущий объём проекта.

### 5.5. NotificationStatus

| Значение | Назначение |
|---|---|
| `CREATED` | Уведомление создано |
| `QUEUED` | Уведомление ожидает отправки или повторной попытки |
| `SENT` | Уведомление отправлено |
| `FAILED` | Отправка завершилась ошибкой |

## 6. Ограничения целостности

### 6.1. Целостность сущностей

- Первичный ключ каждой сущности должен быть уникальным и не может быть NULL.
- Обязательные атрибуты должны быть заполнены.
- Значения перечислений должны соответствовать допустимому набору значений.

### 6.2. Ссылочная целостность

- `ClientContact.client_id` должен ссылаться на существующего клиента.
- `Ticket.client_id` может быть NULL, если клиент не найден.
- `Ticket.assigned_to` может быть NULL, если ответственный не назначен.
- `Notification.ticket_id` должен ссылаться на существующее обращение.
- `Notification.contact_id` должен ссылаться на существующий контакт клиента.

Последнее ограничение означает, что уведомление в текущей модели создаётся только при наличии выбранного контакта. Для клиента, не найденного в CRM, уведомление не отправляется.

### 6.3. Доменная целостность

- `Ticket.status` принимает только значения `TicketStatus`.
- `ClientContact.channel` и `Notification.channel` принимают только значения `Channel`.
- `Operator.status` принимает только значения `OperatorStatus`.
- `Operator.role` принимает только значения `OperatorRole`.
- `Notification.status` принимает только значения `NotificationStatus`.

### 6.4. Уникальность

- `Client.phone_number` уникален в рамках принятой модели.
- `Ticket.source_call_id` уникален для каждого обращения.

Эти ограничения описывают исходную модель данных. Их физическая реализация должна учитывать, что CRM является владельцем клиентских данных и обращений.

## 7. Связь модели данных с бизнес-правилами

| Бизнес-правило | Элементы модели | Пояснение |
|---|---|---|
| BR-002 | `Operator.status`, `Ticket.assigned_to` | Используются для определения подходящего оператора и назначения ответственного |
| BR-003 | `Ticket.source_call_id`, `Ticket.client_id`, `Ticket.status`, `Ticket.created_at` | Используются при поиске существующего открытого обращения и проверке временного условия |
| BR-004 | `ClientContact.used_at`, `ClientContact.channel`, `Notification.contact_id` | Позволяют выбрать последний использованный контакт |
| BR-005 | `Operator.status`, `Operator.is_duty`, `Ticket.assigned_to`, `Ticket.status` | Используются для резервного назначения или фиксации необходимости ручного назначения |

Модель содержит необходимые атрибуты для описания основных бизнес-правил, но сама по себе не определяет полный алгоритм их выполнения.

## 8. Открытые вопросы

Перед окончательным согласованием модели необходимо уточнить:

1. Где физически хранятся данные `Notification` и `Operator`.
2. Как система получает актуальную информацию о смене и доступности оператора.
3. Как технический статус `CREATED` соотносится с бизнес-статусом «Открыто».
4. Как в рамках выбранной модели описывается связь нескольких звонков с одним обращением, не добавляя избыточных сущностей.
5. Как обеспечивается доступность истории использования контактов для применения BR-004.

Эти вопросы зафиксированы для дальнейшей проработки. Новые сущности и дополнительные механизмы не вводятся без необходимости.

## 9. Результаты этапа

В рамках этапа описаны основные сущности, атрибуты, перечисления, связи и ограничения целостности.

Модель данных используется далее для проверки непротиворечивости требований, уточнения нефункциональных требований и построения матрицы трассируемости.
