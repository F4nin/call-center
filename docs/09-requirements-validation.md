# Валидация требований

## 1. Цель

Цель этапа — проверить, что требования соответствуют целям проекта, достаточно полны, однозначны, непротиворечивы и могут быть проверены тестами.

В рамках учебного кейса проводится кабинетная проверка подготовленных артефактов. Формальная инспекция с реальными представителями бизнеса и разработки не проводилась.

## 2. Объекты проверки

Перед передачей требований в разработку проверяются следующие документы:

- `01-vision-and-scope.md` — цели и границы проекта;
- `02-users-and-elicitation.md` — пользователи и подходы к выявлению требований;
- `03-use-cases-and-user-stories.md` — пользовательские истории, сценарий и функциональные требования;
- `04-business-rules.md` — бизнес-правила;
- `05-modeling.md` — контекст и модели поведения;
- `06-data-requirements.md` — модель данных и ограничения;
- `07-non-functional-requirements.md` — нефункциональные требования;
- `08-prioritization.md` — приоритеты и предполагаемый состав релизов.

## 3. Метод проверки

Требования проверяются по шести критериям.

| Критерий | Контрольный вопрос |
|---|---|
| Полнота | Описаны ли основной поток, альтернативные сценарии и исключения? |
| Корректность | Поддерживает ли требование цели проекта и задачи пользователя? |
| Однозначность | Можно ли понять требование только одним способом? |
| Проверяемость | Можно ли определить шаги теста и ожидаемый результат? |
| Согласованность | Не противоречит ли требование другим требованиям, бизнес-правилам и моделям? |
| Трассируемость | Можно ли установить связь требования с целью, сценарием, правилом или тестом? |

## 4. Результаты кабинетной проверки

| ID дефекта | Наблюдение | Решение |
|---|---|---|
| VAL-01 | Условия FR-003 и FR-009 требуют чёткого разграничения: создание обращения при найденном клиенте и обработка случая, когда клиент не найден. | Уточнить область действия FR-003: оно применяется, когда клиент найден и нет открытого обращения для повторного использования. Случай отсутствующего клиента регулируется FR-009. |
| VAL-02 | В документах встречаются бизнес-статус «Открыто» и техническое значение `CREATED`. | Использовать `CREATED` в модели данных и зафиксировать его отображение как «Открыто» в бизнес-терминологии. |
| VAL-03 | NFR-01 ограничивает время от события `CALL_ANSWERED` до создания обращения в CRM, а исходный приёмочный критерий ограничивает двумя секундами время до появления карточки у оператора. Это разные точки измерения. | Сохранить NFR-01 как показатель времени создания обращения. Время появления карточки измерять отдельно; порог для него требует уточнения. |
| VAL-04 | В тесте повторного звонка утверждается, что звонок привязывается к существующему обращению, но текущая модель данных не содержит отдельной сущности звонка и связи для хранения такой привязки. | Проверять, что новое обращение не создано и существующее остаётся доступным. Не считать отдельную связь звонка с обращением реализованной без расширения модели данных. |
| VAL-05 | Для неизвестного клиента используются формулировки «Требует уточнения клиента» и `REQUIRES_CLIENT`. | Использовать `REQUIRES_CLIENT` как технический статус, а «Требует уточнения клиента» — как его отображаемое название. |
| VAL-06 | Для случая отсутствия подходящего оператора встречаются «Требует ручного назначения», «Требует ручной обработки» и `REQUIRES_MANUAL`. | Использовать `REQUIRES_MANUAL` как технический статус. В пользовательском отображении уточнять назначение статуса по контексту: ручное назначение оператора или ручная обработка события. |
| VAL-07 | В исходном документе валидации упоминаются пользовательские истории руководителя и администратора, walkthrough и отчётность. Функциональность руководителя исключена из текущей границы проекта. | Не включать отчётность и отдельные пользовательские функции руководителя в текущую приёмку. Администратор CRM остаётся техническим заинтересованным лицом. |
| VAL-08 | NFR-07 требует журналирования изменений прав операторов, но отдельная функция управления правами не описана в текущем функциональном объёме. | Оставить NFR-07 как требование со статусом `Should`; до реализации уточнить, где выполняется управление правами и какой компонент отвечает за аудит. |

Эти замечания выявлены при самостоятельном анализе документов. Они не являются результатами встречи с заказчиком или формально утверждённым перечнем дефектов.

## 5. Тестовые сценарии требований

Тесты должны покрывать основной сценарий, альтернативные потоки, исключения, бизнес-правила и ключевые нефункциональные требования.

| ID теста | Проверяемые требования | Предусловие и действие | Ожидаемый результат |
|---|---|---|---|
| TST-01 | FR-001, FR-002, FR-003, FR-011 | Телефония подключена, CRM доступна, клиент существует. Передать корректное событие `CALL_ANSWERED`. | Обращение создано в CRM, связано с найденным клиентом, ответственный назначен по правилам, оператор видит карточку, отправка уведомления инициирована. |
| TST-02 | FR-006, BR-003 | Для номера уже существует открытое обращение, созданное в пределах последних 24 часов. Передать повторное событие с тем же номером. | Новое обращение не создаётся, существующее открытое обращение остаётся доступным. |
| TST-03 | FR-009 | Клиента с переданным номером нет в CRM. Передать корректное по формату событие. | Создано обращение без привязки к клиенту, технический статус — `REQUIRES_CLIENT`. |
| TST-04 | FR-010, BR-005 | Все обычные операторы недоступны, дежурный оператор отсутствует. Передать событие. | Обращение не теряется; статус указывает на необходимость ручного назначения или обработки (`REQUIRES_MANUAL`). |
| TST-05 | FR-005, NFR-05 | Сервис уведомлений недоступен. Передать входящий звонок. Затем восстановить сервис. | Обращение создано, уведомление сохранено в очереди и повторно отправлено после восстановления сервиса. |
| TST-06 | FR-008, BR-004 | У клиента есть несколько контактов с разными каналами связи и историей использования. Инициировать выбор контакта для уведомления. | Выбирается контакт, использованный последним, согласно `used_at`. |
| TST-07 | FR-004, BR-002 | В системе есть активный оператор, не находящийся на перерыве. Выполнить назначение ответственного. | Ответственный выбирается среди операторов, удовлетворяющих условиям бизнес-правила. |

## 6. Приёмочные критерии

Приёмочные критерии определяют, что должно быть выполнено для принятия основного сценария. Приведённые критерии являются проектной версией и требуют согласования с заказчиком при реальном внедрении.

| ID | Критерий |
|---|---|
| AC-01 | При входящем звонке с известного и корректного номера система находит клиента, создаёт обращение, назначает ответственного по бизнес-правилам и инициирует отправку уведомления. |
| AC-02 | Обращение создаётся в CRM не позднее чем через 2 секунды после получения события `CALL_ANSWERED`. Время отображения карточки оператору измеряется отдельно. |
| AC-03 | Повторный звонок с того же номера в пределах 24 часов при наличии открытого обращения не приводит к созданию нового обращения. |
| AC-04 | При недоступности сервиса уведомлений обращение сохраняется, а уведомление помещается в очередь для повторной отправки. |
| AC-05 | Если клиент не найден, обращение создаётся без привязки к клиенту со статусом `REQUIRES_CLIENT`. |
| AC-06 | Если нет доступного обычного оператора и дежурного оператора, обращение не теряется и требует ручного назначения или обработки. |
| AC-07 | При некорректном номере система не создаёт обращение и обрабатывает ошибку согласно FR-012. |

## 8. План рецензирования

В реальном проекте рецензирование рекомендуется проводить с участием следующих ролей:

| Роль | Задача |
|---|---|
| Автор требований / системный аналитик | Представляет документы, объясняет решения и фиксирует замечания. |
| Модератор | Следит за регламентом встречи и фокусом обсуждения. |
| Представитель бизнеса | Подтверждает соответствие требованиям бизнес-целям. |
| Представитель пользователей | Проверяет реалистичность пользовательских сценариев. |
| Разработчик интеграций | Оценивает техническую реализуемость и ограничения интеграций. |
| Тестировщик | Проверяет тестируемость требований и полноту сценариев. |
| Архитектор | Проверяет влияние нефункциональных требований на архитектуру. |

Для основного сценария UC-01 подходит формальная инспекция. Для нефункциональных требований полезна отдельная техническая рецензия.

В текущем учебном кейсе этот план описывает предполагаемый процесс. Указанные роли не означают, что рецензирование действительно проводилось с такими участниками.

## 9. Критерии завершения валидации

Перед передачей требований в разработку следует убедиться, что:

- все блокирующие противоречия устранены или явно отмечены как открытые вопросы;
- каждому критичному требованию соответствует тест или проверяемый критерий;
- технические статусы и их бизнес-отображение согласованы;
- открытые вопросы, влияющие на архитектуру или приёмку, зафиксированы;
- история изменений требований обновлена;
- статус каждого требования отражает фактическое состояние проверки.

До согласования с реальными заинтересованными лицами требования не следует обозначать как утверждённые заказчиком.

## 10. Итог

Кабинетная проверка помогает выявить несовпадения между функциональными требованиями, бизнес-правилами, моделью данных, нефункциональными требованиями и приёмочными сценариями до начала разработки.

Для этого кейса наиболее важны согласование времени создания обращения и отображения карточки, отображаемых названий статусов, обработки повторного звонка и границ текущего проекта.

Результат этапа — набор тестовых сценариев, проектные приёмочные критерии и перечень замечаний для дальнейшей проработки. Формальное утверждение требований остаётся отдельным шагом.
