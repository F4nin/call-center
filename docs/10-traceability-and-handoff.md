# Трассируемость требований и передача в разработку

## 1. Назначение

Цель этапа — связать бизнес-цели, пользовательские задачи, сценарии, функциональные и нефункциональные требования, бизнес-правила и тесты. Это позволяет проверить, зачем существует каждое требование, как оно будет реализовано и каким способом проверяется результат.

Документ описывает подготовку к передаче требований в разработку в рамках учебного кейса. Требования не считаются утверждёнными реальным заказчиком, реализованными или проверенными в системе.

## 2. Полная цепочка трассируемости

Основная цепочка для проекта:

**Бизнес-проблема → бизнес-цель → User Story → Use Case → FR / BR / NFR → тест → критерий приёмки.**

| Элемент | Идентификатор | Содержание |
|---|---|---|
| Бизнес-проблема | — | Обращения могут теряться из-за ручного поиска клиента, создания обращения, назначения ответственного и отправки уведомления. |
| Бизнес-цель | BG-01 | Снизить долю потерянных обращений до 5% в месяц через 3 месяца после внедрения. |
| Пользовательская история | US-01 | Оператор хочет сразу видеть карточку клиента и обращение, чтобы не выполнять ручной поиск. |
| Пользовательская история | US-02 | Клиент должен получать уведомление о приёме обращения. |
| Use Case | UC-01 | Обработать входящий звонок. |
| Функциональные требования | FR-001, FR-002, FR-003, FR-011 | Получить событие, найти клиента, создать обращение и показать карточку оператору. |
| Бизнес-правила | BR-002, BR-003, BR-004, BR-005 | Назначить ответственного по правилам, обработать повторное обращение, выбрать последний использованный контакт и учесть дежурного оператора. |
| Тесты | TST-01, TST-02, TST-06, TST-07 | Проверить основной поток, повторное обращение, выбор контакта и назначение ответственного. |
| Приёмочные критерии | AC-01, AC-03 | Проверить автоматическую обработку известного клиента и отсутствие нового обращения при повторном звонке. |
| Приёмочные тесты | AT-01, AT-02 | Проверить основной сценарий и повторный звонок. |

Эта цепочка показывает связь требований с бизнес-проблемой, но не означает, что все бизнес-цели уже достигнуты. Для BG-01 потребуется измерение фактической доли потерянных обращений после внедрения.

## 7. Жизненный цикл требований

Для управления требованиями используются следующие статусы.

| Статус | Значение |
|---|---|
| Предложено | Требование сформулировано и зафиксировано в документации. |
| Утверждено | Требование согласовано после валидации с уполномоченными заинтересованными лицами. |
| Реализовано | Требование реализовано в программном решении. |
| Проверено | Реализация прошла соответствующие проверки и принята по заданным критериям. |
| Отложено | Реализация перенесена на последующий релиз. |
| Отклонено | Принято решение не реализовывать требование. |

На текущем этапе требования описаны в рамках учебного кейса. Статусы «Утверждено», «Реализовано» и «Проверено» не присваиваются без соответствующих фактических действий.

Для BR-001 применяется пометка «Вне текущего объёма», поскольку правило относится к исключённому сценарию исходящих звонков. Это не означает, что его реализация обязательно запланирована на будущий релиз.

### Рекомендуемый порядок передачи

1. Устранить блокирующие несогласованности и явно зарегистрировать оставшиеся открытые вопросы.
2. Согласовать требования и критерии приёмки с реальными заинтересованными лицами, если проект переходит в реальную разработку.
3. Создать задачи в трекере для реализации и проверки требований.
4. Связать каждую задачу с ID требований — например, `FR-003`, `BR-003` или `NFR-01`.
5. По мере работы обновлять статусы требований и сохранять связь с тестами и результатами проверок.

В учебном репозитории создание задач в Jira, Confluence или другом трекере не предполагается обязательным: достаточно показать подход и связи между требованиями.

## 9. Переиспользуемые артефакты

В проекте выделены следующие материалы, структуру которых можно повторно использовать в других учебных или рабочих проектах:

- шаблон Use Case;
- реестр бизнес-правил;
- словарь данных;
- таблица событий и реакций системы;
- ERD и исходники диаграмм;
- чек-лист валидации требований;
- таблицы трассируемости;
- шаблон тестовых и приёмочных критериев;
- типовые требования по защите интеграций, логированию и доступности.

Переиспользовать можно структуру и шаблоны. Сами бизнес-правила, поля данных, пороги качества и критерии приёмки необходимо заново проверять для каждого проекта.

## 10. Открытые вопросы перед полноценной передачей в разработку

1. Как хранить сведения о событии и его состоянии, если CRM недоступна и обращение ещё не создано?
2. Как в модели данных представлять повторные звонки, которые используют уже открытое обращение, если требуется сохранить связь каждого звонка с обращением?
3. Как отдельно измерять время создания обращения и время появления карточки у оператора?
4. Как рассчитывать бизнес-метрики потерь обращений, ошибок данных, среднего времени обработки и NPS?
5. Где управляются права операторов и какой компонент должен вести аудит их изменений?
6. Какие критерии приёмки и дополнительные тесты потребуются для FR-008, FR-010 и FR-012?

Эти вопросы не требуют автоматически добавлять новые сущности или функции. Сначала необходимо определить, какие из них действительно нужны в границах проекта.

## 11. Итог

По результатам учебного кейса подготовлены основные артефакты системного анализа: концепция и границы, описание пользователей, пользовательские истории и сценарии, функциональные требования, бизнес-правила, модели, требования к данным и качеству, приоритизация, валидация и матрица трассируемости.

Матрица связывает бизнес-цели с требованиями и проверками, помогает выявлять пробелы и определяет, какие материалы предназначены для разных участников разработки.

Комплект можно рассматривать как предварительную спецификацию для учебной передачи в разработку. Для реального проекта потребуется согласование с заинтересованными лицами, разрешение открытых вопросов и фактическое выполнение тестов.
