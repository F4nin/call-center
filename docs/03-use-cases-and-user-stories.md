# 03. Use Cases и User Stories

**Проект:** Автоматизация обработки входящих обращений Call-центра  
**Тип проекта:** Самостоятельный учебный кейс по системному анализу  
**Статус документа:** Учебная версия

## 1. Цель документа

Документ описывает пользовательские потребности и сценарии взаимодействия с системой автоматизации обработки входящих звонков.

В рамках этапа определяются:
- пользовательские истории (User Stories);
- основной сценарий использования (Use Case);
- альтернативные потоки и исключительные ситуации;
- предварительный перечень функциональных требований.


## 2. User Stories

### US-01. Просмотр информации о клиенте и обращении

**Как** оператор Call-центра,  
**я хочу** видеть карточку клиента и информацию об обращении при поступлении входящего звонка,  
**чтобы** быстро получить необходимый контекст и не выполнять поиск клиента вручную.

### US-02. Получение уведомления о регистрации обращения

**Как** клиент,  
**я хочу** получать уведомление о регистрации обращения,  
**чтобы** понимать, что мой вопрос зафиксирован.

Уведомление отправляется по доступному контакту клиента в соответствии с установленными бизнес-правилами.

## 3. Use Case UC-01. Обработать входящий звонок

### 3.1. Основная информация

| Поле | Описание |
|---|---|
| ID | UC-01 |
| Название | Обработать входящий звонок |
| Цель | Автоматизировать регистрацию и первичную обработку входящего звонка |
| Инициирующая внешняя система | Телефония |
| Основной пользователь | Оператор Call-центра |
| Вторичные системы | CRM, сервис уведомлений |
| Триггер | Получение события `CALL_ANSWERED` от телефонии |

Телефония инициирует обработку события. Оператор является основным пользователем, который получает результат обработки.

### 3.2. Предусловия

- Телефония настроена на передачу событий о входящих звонках.
- Сервис обработки обращений настроен для взаимодействия с CRM и сервисом уведомлений.
- Системе доступны необходимые настройки интеграций.

Доступность CRM и сервиса уведомлений не является обязательным предусловием: недоступность этих систем рассматривается в альтернативных и исключительных потоках.

### 3.3. Постусловия успешного выполнения

- Обращение создано в CRM либо новый звонок привязан к уже существующему открытому обращению в соответствии с бизнес-правилом обработки повторных звонков.
- Ответственный назначен согласно установленным правилам либо обращение отмечено как требующее ручного назначения.
- Уведомление клиенту отправлено либо помещено в очередь повторной отправки.
- Оператору доступна информация о клиенте и обращении.

### 3.4. Основной поток

1. Телефония отправляет событие `CALL_ANSWERED` с номером телефона клиента.
2. Сервис получает событие и извлекает номер телефона.
3. Сервис проверяет корректность номера.
4. Сервис выполняет поиск клиента в CRM по номеру телефона.
5. Система проверяет наличие открытого обращения по тому же номеру за последние 24 часа.
6. Если подходящее открытое обращение существует, система связывает новый звонок с ним и не создаёт новое обращение. Иначе система создаёт обращение в CRM со статусом «Открыто» и заполняет необходимые поля.
7. Система определяет ответственного в соответствии с бизнес-правилом назначения оператора.
8. Система назначает ответственного либо отмечает обращение как требующее ручного назначения.
9. Система определяет контакт и канал связи клиента согласно бизнес-правилам.
10. Система инициирует отправку уведомления клиенту.
11. Система отображает оператору информацию о клиенте и обращении.

Если в ходе выполнения основного потока возникает ситуация, описанная в альтернативном или исключительном потоке, система действует согласно соответствующему сценарию.

### 3.5. Альтернативные потоки

#### A1. У клиента несколько контактов

**Условие:** в CRM найден клиент, у которого несколько контактов или каналов связи.

1. Система определяет последний использованный контакт или канал связи.
2. Система выбирает его для отправки уведомления.
3. Обработка продолжается с шага 10 основного потока.

Связанное бизнес-правило: BR-004.

#### A2. Нет подходящего активного оператора

**Условие:** среди операторов нет подходящего для назначения сотрудника.

1. Система проверяет наличие дежурного оператора.
2. Если дежурный оператор доступен, система назначает его ответственным.
3. Если дежурный оператор отсутствует, система отмечает обращение как «Требует ручного назначения».
4. Система продолжает обработку обращения.

Связанные бизнес-правила: BR-002, BR-005.

### 3.6. Исключительные потоки

#### E1. Клиент не найден

**Условие:** CRM не содержит клиента с указанным номером телефона.

1. Система создаёт обращение без привязки к клиенту.
2. Система присваивает обращению статус «Требует уточнения клиента».
3. Система отображает оператору сообщение о необходимости уточнить данные клиента.
4. Система не отправляет уведомление, поскольку связанный контакт клиента не определён.

**Результат:** обращение сохранено в CRM и доступно оператору для дальнейшей обработки.

#### E2. Получен некорректный номер телефона

**Условие:** событие телефонии содержит номер, не прошедший проверку корректности.

1. Система фиксирует ошибку обработки события.
2. Обращение не создаётся.
3. Оператору отображается предупреждение о некорректном номере.

**Результат:** некорректное событие не приводит к созданию обращения с ошибочными данными.

#### E3. CRM недоступна

**Условие:** система не может выполнить запрос к CRM.

1. Система повторяет запрос до трёх раз с экспоненциальной задержкой.
2. Если CRM по-прежнему недоступна, система фиксирует событие как требующее ручной обработки.
3. Оператор получает сообщение о сбое.

**Результат:** событие не считается успешно обработанным, а необходимость ручной обработки явно зафиксирована.

#### E4. Сервис уведомлений недоступен

**Условие:** невозможно отправить уведомление через внешний сервис.

1. Система сохраняет уведомление в очередь повторной отправки.
2. Созданное обращение сохраняется.
3. Повторная отправка выполняется по установленному расписанию.

**Результат:** недоступность сервиса уведомлений не приводит к потере уже созданного обращения.

### 3.7. Бизнес-правила сценария

| ID | Правило | Применение в сценарии |
|---|---|---|
| BR-002 | Назначение только подходящего оператора, находящегося в активной смене и не на перерыве | Определение основного ответственного |
| BR-003 | Если звонок с того же номера поступает в течение 24 часов и существует открытое обращение, новый звонок привязывается к существующему обращению | Предотвращение создания повторного обращения |
| BR-004 | При нескольких контактах используется последний использованный канал связи | Выбор контакта для уведомления |
| BR-005 | Если подходящий ответственный недоступен, назначается дежурный оператор; при его отсутствии требуется ручное назначение | Резервный вариант назначения |

Правило BR-001 об ограничении количества исходящих звонков не относится к рассматриваемому сценарию входящих звонков и исключено из текущего объёма.

## 4. Функциональные требования

Функциональные требования конкретизируют поведение системы, описанное в UC-01.

| ID | Функциональное требование | Источник |
|---|---|---|
| FR-001 | При получении события `CALL_ANSWERED` система должна извлечь номер телефона клиента из данных события | UC-01, шаги 1–2 |
| FR-002 | Система должна выполнять поиск клиента в CRM по номеру телефона | UC-01, шаг 4 |
| FR-003 | Если клиент найден и подходящего открытого обращения нет, система должна создать обращение в CRM со статусом «Открыто» и заполнить необходимые поля | UC-01, шаг 6 |
| FR-004 | Система должна назначить ответственного из числа операторов, находящихся в активной смене и не на перерыве | UC-01, шаг 7; BR-002 |
| FR-005 | Если сервис уведомлений недоступен, система должна поместить уведомление в очередь повторной отправки | UC-01, исключительный поток E4 |
| FR-006 | Если в течение 24 часов поступает звонок с того же номера и существует открытое обращение, система должна связать новый звонок с существующим обращением, не создавая новое | UC-01, шаг 5; BR-003 |
| FR-007 | После регистрации обращения система должна инициировать отправку уведомления клиенту | UC-01, шаг 10; US-02 |
| FR-008 | При наличии нескольких контактов система должна выбрать последний использованный контакт или канал связи для отправки уведомления | UC-01, альтернативный поток A1; BR-004 |
| FR-009 | Если клиент не найден в CRM, система должна создать обращение без привязки к клиенту и присвоить статус «Требует уточнения клиента» | UC-01, исключительный поток E1 |
| FR-010 | Если подходящий активный оператор отсутствует, система должна назначить дежурного оператора; при его отсутствии обращение получает статус «Требует ручного назначения» | UC-01, альтернативный поток A2; BR-005 |
| FR-011 | Система должна отображать оператору информацию о клиенте и созданном либо найденном обращении | UC-01, шаг 11; US-01 |
| FR-012 | Если номер телефона некорректен, система должна зафиксировать ошибку обработки, не создавать обращение и уведомить оператора | UC-01, исключительный поток E2 |

**Примечание.** Статус «Открыто» используется как бизнес-обозначение состояния обращения. Его соответствие техническому значению статуса необходимо согласовать в словаре данных на этапе 6.
