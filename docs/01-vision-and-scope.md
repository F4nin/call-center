# 01. Vision and Scope — Концепция и границы проекта

**Проект:** Автоматизация обработки входящих обращений Call-центра  
**Тип проекта:** Самостоятельный учебный кейс по системному анализу  
**Статус документа:** Учебная версия  
**Версия:** 1.0

## 1. Бизнес-проблема

В рамках учебного сценария рассматривается работа Call-центра, в котором обработка входящих звонков во многом зависит от ручных действий оператора.

При поступлении звонка оператору необходимо найти клиента в CRM, создать обращение, назначить ответственного и отправить клиенту уведомление.

Такой процесс может увеличивать время обработки звонка, приводить к ошибкам при заполнении данных и повышать вероятность потери обращений.

В исходной концепции кейса предполагается, что из-за ручной обработки теряется до 30% входящих обращений.

**Проблема, которую решает проект:** отсутствие автоматизированного процесса регистрации и первичной обработки входящих звонков.

Указанные показатели и описание ситуации являются допущениями учебного сценария и не основаны на исследовании реальной компании.

## 2. Видение продукта

Создать сервис автоматизации обработки входящих звонков Call-центра, который взаимодействует с телефонией, CRM и внешним сервисом уведомлений.

При поступлении входящего звонка сервис должен автоматически получить событие, найти клиента в CRM, создать обращение, назначить ответственного в соответствии с бизнес-правилами и инициировать отправку клиентского уведомления.

В результате оператор получает карточку клиента и информацию об обращении без необходимости выполнять все перечисленные действия вручную.

Ожидаемый эффект — сокращение времени первичной обработки звонка, уменьшение количества ошибок и снижение вероятности потери обращений.

## 3. Бизнес-цели и критерии успеха

В рамках учебного сценария определены следующие цели.

| ID | Бизнес-цель | Критерий успеха |
|---|---|---|
| BG-01 | Снизить количество потерянных обращений | Доля потерянных обращений — не более 5% в месяц через 3 месяца после внедрения |
| BG-02 | Сократить время обработки входящего звонка | Среднее время обработки — не более 30 секунд вместо исходных 3 минут |
| BG-03 | Снизить количество ошибок в клиентских данных | Доля обращений с ошибками в клиентских данных — не более 2% |
| BG-04 | Повысить удовлетворённость клиентов | NPS — не ниже 40 через 6 месяцев после внедрения |

**Примечание к показателям.** Значения являются целевыми ориентирами учебного проекта. Методика расчёта доли потерянных обращений, ошибок и NPS в рамках текущего кейса не определена.

Для показателя времени обработки необходимо отдельно зафиксировать границы измерения: он не должен автоматически трактоваться как время ответа системы на интеграционный запрос. Техническая задержка обработки события рассматривается отдельно на этапе нефункциональных требований.

## 4. Контекст системы

Решение взаимодействует со следующими внешними системами и пользователями.

| Участник или система | Назначение |
|---|---|
| Телефония | Передаёт событие о входящем звонке и номер телефона клиента |
| CRM | Хранит клиентские данные и обращения; используется для поиска клиента и создания обращения |
| Сервис уведомлений | Обеспечивает отправку SMS, email или push-уведомлений |
| Оператор Call-центра | Просматривает карточку клиента и информацию об обращении, работает с обращением |

### 4.1. Общая последовательность работы

1. Телефония передаёт событие `CALL_ANSWERED`.
2. Сервис получает событие и извлекает номер телефона.
3. Сервис выполняет поиск клиента в CRM.
4. Сервис инициирует создание обращения в CRM.
5. Сервис определяет и назначает ответственного согласно бизнес-правилам.
6. Сервис инициирует отправку уведомления клиенту.
7. Карточка клиента и информация об обращении становятся доступны оператору.

Подробная логика основного и альтернативных сценариев описывается в документе `03-use-cases-and-user-stories.md`.

## 5. Основные функциональные возможности

В рамках проекта рассматриваются следующие возможности:

- приём событий о входящих звонках от телефонии;
- поиск клиента в CRM по номеру телефона;
- создание обращения с необходимыми атрибутами;
- назначение ответственного по бизнес-правилам;
- обработка повторных звонков в соответствии с установленным правилом;
- отправка клиентского уведомления;
- отображение карточки клиента и обращения оператору;
- обработка ситуаций, когда клиент не найден, данные звонка некорректны или внешняя система недоступна.

Подробные требования к каждой возможности будут сформулированы на последующих этапах.

## 6. Границы проекта

### 6.1. В рамках проекта

- Интеграция с телефонией для получения событий о входящих звонках.
- Взаимодействие с CRM для поиска клиентов и создания обращений.
- Интеграция с сервисом SMS/email/push-уведомлений.
- Реализация правил назначения ответственного.
- Обработка повторных звонков в соответствии с бизнес-правилами.
- Обработка ошибок интеграционного взаимодействия.
- Отображение информации о клиенте и обращении оператору.

## 7. Допущения и зависимости

### 7.1. Допущения

Для проработки учебного сценария принимаются следующие допущения:

- телефония поддерживает передачу событий о звонках через API или webhook;
- событие `CALL_ANSWERED` содержит номер телефона клиента;
- в CRM существует справочник клиентов с номерами телефонов;
- CRM предоставляет возможность искать клиента и создавать обращение;
- доступен внешний сервис для отправки клиентских уведомлений;
- правила назначения ответственного определяются в рамках рассматриваемого кейса.

Эти условия приняты для моделирования системы и не подтверждены проверкой реальных API или взаимодействием с владельцами внешних систем.

### 7.2. Зависимости

На работу решения могут влиять:

- доступность и корректность API телефонии;
- доступность CRM и корректность хранящихся в ней клиентских данных;
- доступность внешнего сервиса уведомлений;
- полнота и непротиворечивость правил назначения ответственного.

Конкретные требования к обработке отказов и восстановлению после сбоев рассматриваются в функциональных и нефункциональных требованиях.
